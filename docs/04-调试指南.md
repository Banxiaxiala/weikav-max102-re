# 调试入口全图 —— MAX102 的三层可观测性

> 从"最浅、最安全"到"最深、最危险"排列。**建议按顺序逐层深入，不要一开始就上 SWD。**
>
> 本文所有地址、键位链、协议字段均来自实机固件读取与反编译，非推测。

---

## 0. 三层总览

| 层 | 入口 | 需要拆机 | 需要焊线 | 能做什么 | 能破坏什么 |
|---|---|---|---|---|---|
| **L1** | USB HID / VIA 协议 | ❌ | ❌ | 读键位、读宏、读协议版本、改键 | 改键（可撤销） |
| **L2** | ROM DFU bootloader | ❌ | ❌ | **完整读 Flash、完整写 Flash、救砖** | **刷坏固件** |
| **L3** | SWD（CON2 四针） | ✅ | ✅ | 连 CPU 核、跑断点、读 RAM、单步 | 需外部供电，操作失误可锁片 |

> **关键顺序**：L1 随时可用；L2 是救砖底线，**进 L2 之前必须先备份**；L3 只在 L2 修不好时用。

---

## 1. L1 —— USB HID / VIA 协议

### 1.1 怎么进去

不需要"进入"，键盘正常工作时就开着。

```
物理条件：USB 线连接 + 电源开关拨到 ON
传输模式：按 FN + T 切到「有线 / USB」模式
```

USB 标识：

| 模式 | VID | PID |
|---|---|---|
| 正常工作 | `0x342D` | `0xE537` |
| DFU | `0x342D` | `0xDFA0` |

HID 接口布局：

```
interface 0: usage_page=1      usage=6    ← 标准键盘
interface 1: usage_page=65376  usage=97   ← VIA 通道（REPORT_SIZE=33）
interface 2: usage_page=1/12/...          ← 多媒体 / 系统控制
```

**VIA 通道特征**：`usage_page=0xFF60`、`usage=0x61`、报告长度 33 字节（1 字节 report ID + 32 字节载荷）。

### 1.2 协议参数

| 项 | 值 |
|---|---|
| VIA 协议版本 | **12** |
| 层数 | **5**（网页驱动只暴露 4 层，第 5 层隐藏） |
| 矩阵 | **6 行 × 19 列** |
| 键位缓冲 | 每层 172 键 × 2 字节（固件按更大矩阵分配） |
| 宏数量 | 16 |
| 宏缓冲 | 1984 字节 |
| 固件版本字段 | `0.0.0`（厂家未填） |

### 1.3 报文格式

```
[0x00] [cmd] [payload...]
  ↑      ↑
  report ID（固定 0）
```

响应同样走 32 字节 HID 报告。

### 1.4 45 条命令全表

| `0x0D` | `MACRO_GET_BUFFER_SIZE` | ✅ |

> 但必须自己发 HID 报文，普通 VIA 网页不提供。

```c

#define MAGIC_ADDR (unsigned long *)(SYMVAL(__ram0_end__) - 4)
// 写 magic → NVIC_SystemReset → 启动时检测 magic → 跳 0x1FFFE000
```

| 键码 | 索引 | 动作 | 处理函数 |

| `0x7E0A` | 10 | 未细查 | `FUN_08004d93` |

| `0x7E0E` | 14 | 未细查 | `FUN_08004d39` |

这些在 VIA 界面里**选不到**，但可以通过 cmd `0x05` 直接写进去。

## 2. L2 —— ROM DFU bootloader（救砖底线）

### 2.1 原理

WB32 的 DFU bootloader **固化在 ROM**，地址 `0x1FFFE000`。它不属于用户 Flash，
不可擦写、不会被刷坏，所以**只要芯片没物理损坏，就永远能救回来**。

这一点是本项目最重要的安全前提：

- ✅ 不需要 OpenOCD
- ✅ 不需要拆焊 Flash
- ✅ 不需要专用编程器
- ✅ 即使把 `0x08000000` 起 256KB 全写成 0xFF 也能救

### 2.2 进 DFU 的三种方法

#### 方法 A：隐藏 BOOT 层按键链（推荐，无需工具）

固件藏了一个隐藏的第 5 层。从实读 keymap 反推出的键位链：

```
Layer 0  matrix(5,9)  = MO(1)      ← FN 键
Layer 1  matrix(4,12) = MO(4)      ← FN 层里的右 Shift 位置
Layer 4  matrix(0,0)  = QK_BOOT    ← 第 4 层的 ESC 位置
```

**操作：按住 FN → 按住右 Shift → 点一下 ESC**

成功标志（键盘完全停止工作，打不了字）：

```bash
wb32-dfu-updater_cli.exe -l
# Found DFU: [0x342D:0xDFA0] ver=0x0100, devnum=7, cfg=1, intf=0
```

#### 方法 B：VIA 命令 `0x0B`

发一条 `BOOTLOADER_JUMP` HID 报文。等价于方法 A，但要自己写代码。

#### 方法 C：SWD 硬跳（仅在 L3 可用时）

用调试器把 PC 设为 `0x1FFFE000` 的 Reset 向量，或直接 `NVIC_SystemReset()` 配合 magic 写入 `__ram0_end__ - 4`。

### 2.3 驱动安装（需要管理员）

DFU 模式需要 WinUSB 驱动，**只绑定 `USB\VID_342D&PID_DFA0`**：

```batch
cd wb_dfu_usb_driver_v1.0.0.0
dpinst_amd64.exe
```

注意：

- **必须先让键盘进 DFU，装驱动才有意义**
- 正常模式下装不了，也不该装
- 卸载：`dpinst_amd64.exe /u wb_device_in_dfu_mode.inf`

### 2.4 读取固件

```bash
# 确认设备在线
wb32-dfu-updater_cli.exe -l

# 全片 256KB 读取（实测 0.6 秒）
wb32-dfu-updater_cli.exe -U max102_stock_256k.bin -Z 262144

# 复位回正常模式
wb32-dfu-updater_cli.exe -R
```

⚠️ **`-Z` 必须显式给**，工具不会自动探测容量：

- 给大了（>256KB）→ 读越界，可能报错或读到垃圾
- 给少了（<256KB）→ 备份不完整，救砖时恢复不全

### 2.5 校验备份完整性

```bash
md5sum max102_stock_256k.bin
# 期望：4014df74ebde3479afcfc90460eae28a

sha256sum max102_stock_256k.bin
# 期望：ac842a1134477ad2dc1085b9429fdef0c0cdc0d9554ccecbb51a75968ef9d1b5

# 有效边界检查：0x11000 之后应全为 0x00
xxd -s 0x11000 -l 64 max102_stock_256k.bin
```

本仓库提供的固件：

| 文件 | 大小 | MD5 | 用途 |
|---|---|---|---|
| `firmware/max102_stock_256k.bin` | 262,144 B | `4014df74ebde3479afcfc90460eae28a` | **全片备份（救命用）** |
| `firmware/max102_stock_trimmed.bin` | 69,632 B | `72feb0cbda334b8bb66a41f0ef39def2` | 有效区（反编译用） |

**有效边界**：

```
0x08000000  向量表起点
0x08010D33  最后一个非零字节
0x08011000  之后全部为 0x00（注意不是常见的 0xFF，是有效擦除态）
```

> 两次独立 DFU 读取 MD5 完全一致，备份可信。

### 2.6 写入（刷回 / 刷第三方）

```bash
# 1. 进 DFU（方法 A/B/C 任一）
# 2. 确认设备
wb32-dfu-updater_cli.exe -l

# 3. 写入 —— 地址必须从 0x08000000 开始
wb32-dfu-updater_cli.exe -D firmware/max102_stock_trimmed.bin -s 0x08000000

# 4. 复位
wb32-dfu-updater_cli.exe -R
```

⚠️ **`-s` 起始地址必须是 `0x08000000`**。写偏了就是砖，虽然还能用 DFU 救，但要重来一遍。

### 2.7 救砖流程（键盘彻底不工作）

```
键盘无反应
    │
    ├─ 还能进 DFU？ ── 是 ──→ 直接刷回 max102_stock_256k.bin，完事
    │
    └─ 否
        │
        ├─ 拔掉电池排线，等 10 秒，重新插上
        │    （有些砖状态需要冷启动才能响应 DFU 握手）
        │
        ├─ 换一根数据线 / 换 USB 口 / 换电脑
        │    （劣质线只供电不传数据，是最常见的假故障）
        │
        ├─ 直接按住 BOOT 组合键再插 USB
        │    （FN + 右 Shift 按住，插线，再点 ESC）
        │
        └─ 还是不行 ──→ 只能上 L3 SWD
```

**为什么 HardFault 会导致砖**：反编译确认固件的 NMI / HardFault / MemManage /
BusFault / UsageFault 全部是**默认弱符号**（`b .` 死循环）：

| 向量 | 地址 | 状态 |
|---|---|---|
| Reset_Handler | `0x080001B9` | ✅ 实现 |
| NMI / HardFault / MemManage / BusFault / UsageFault | `0x080001BB` | ⚠️ `b .` 死循环 |
| PendSV | `0x080001BB` | ⚠️ 默认 |

也就是说**一旦触发硬件异常，固件没有任何自救逻辑，也不打印任何信息**。
这就是为什么刷机出错后只能靠 DFU / SWD —— 它设计上就没打算让你从软件层恢复。

## 3. L3 —— SWD 调试（CON2 四针）

### 3.1 焊盘位置

拆机后 PCB 上可见：

```
CON2:  GND  SWCLK  SWDIO  3.3V
       ○    ○      ○      ○
```

**4 线全部裸露，未焊排针**。另有 `CON3` 提供额外 3.3V 测试点。

> ⚠️ **拆机前必须先断开电池排线**（10000mAh 锂电池，短路会烧板甚至起火）。

### 3.2 接线

| CON2 | 接调试器 |
|---|---|
| GND | GND（**必须共地，先接这根**） |
| SWCLK | SWCLK |
| SWDIO | SWDIO |
| 3.3V | 3.3V 参考（**是否供电看情况，见下**） |

**供电注意**：

- 先用键盘自己的电池/USB 供电，调试器只接 GND / SWCLK / SWDIO 三根
- 只有当键盘完全没电、需要调试器供电时才接 3.3V
- 调试器 3.3V 和键盘电池同时供电可能造成回灌，**非必要不接**

### 3.3 关键限制 —— OpenOCD 不能读写 Flash

**OpenOCD 没有 WB32 的 flash 驱动**（`src/flash/nor/` 里没有 `wb32` 相关实现）。

这意味着 SWD 的能力边界是：

| 能做 | 不能做 |
|---|---|
| ✅ 连接 CPU 核（Cortex-M3） | ❌ 擦除 Flash |
| ✅ 读/写 RAM | ❌ 写入 Flash |
| ✅ 设置断点、单步 | ❌ 替代 DFU 做固件备份 |
| ✅ 读寄存器、看外设 | ❌ 用 `flash write_image` |

**结论：SWD 是"看"和"控"的工具，不是"刷"的工具。刷固件永远走 L2 DFU。**

### 3.4 连接参数

```
接口     : SWD（不是 JTAG）
目标     : Cortex-M3
Flash 基址: 0x08000000
RAM 基址  : 0x20000000
Initial SP: 0x20000400
ROM bootloader: 0x1FFFE000
```

OpenOCD 配置示例（`openocd.cfg`）：

```tcl
source [find interface/cmsis-dap.cfg]
# 或 source [find interface/stlink.cfg]

transport select swd
adapter speed 1000

# WB32FQ95 可复用 STM32F1 的核定义（同为 Cortex-M3）
set _CHIPNAME wb32fq95
set _CPUTAPID 0x2ba01477
swj_newdap $_CHIPNAME cpu -irlen 4 -ircapture 0x1 -irmask 0xf -expected-id $_CPUTAPID
dap create $_CHIPNAME.dap -chain-position $_CHIPNAME.cpu
target create $_CHIPNAME.cpu cortex_m -dap $_CHIPNAME.dap
```

启动：

```bash
openocd -f openocd.cfg
```

### 3.5 有用的 SWD 操作

```tcl
# telnet 4444 连上后

# 看当前 PC / SP
reg pc
reg sp

# 读向量表，确认 Flash 内容正常
mdw 0x08000000 4
# 期望第一字 = 0x20000400（Initial SP）
# 期望第二字 = 0x080001B9（Reset_Handler，Thumb 位已置）

# 读 ROM bootloader 向量表（确认 DFU 还在）
mdw 0x1FFFE000 4

# 直接跳到 DFU bootloader（救砖用）
# 前提：确认 0x1FFFE004 处的 Reset 向量有效
reg pc 0x1FFFE005
resume
```

### 3.6 什么时候真的需要 L3

| 场景 | 需要 L3 吗 |
|---|---|
| 想备份固件 | ❌ 用 DFU，更快更完整 |
| 想刷固件 | ❌ 用 DFU，SWD 根本刷不了 |
| 键盘刷砖、DFU 也不响应 | ✅ 唯一剩下的路 |
| 想看 RAM 里的实时状态（比如无线协议收发缓冲） | ✅ 有价值 |
| 想在任意地址下断点、单步跟固件逻辑 | ✅ 有价值 |
| 想动态验证反编译结论 | ✅ 有价值 |

## 4. UART —— 主控 ↔ 无线模块（第四层观测点）

这一层不是"调试口"，但它是**唯一能观测三模功能内部状态**的地方。

### 4.1 链路

```
USB ──► WB32FQ95 ──UART3 @115200 8N1──► FR8003A ──► BT / 2.4G
         (键盘主控)    PC10(TX) / PC11(RX)   (无线 SoC)
```

固件侧参数（已从固件确认）：

| 项 | 值 | 证据 |
|---|---|---|
| 外设 | **UART3**（基址 `0x40008400`） | 固件中唯一被引用的 UART 基址 |
| 中断 | **IRQ32**（`IRQ32_Handler` @ `0x0800E6B8`） | 最大 IRQ，含 RX/TX 环形缓冲 |
| 波特率 | **115200 8N1** | `FUN_080034d4` 首指令 `mov.w r0, #0x1c200` |
| GPIO base | `0x40000800` = GPIOC | 已与官方 `wb32fq95xx.h` 核对 |
| 引脚 | **PC10 / PC11** | `FUN_0800be84` 配 bit10 + bit11 为 AF 模式 |

### 4.2 怎么接逻辑分析仪

1. 拆机，找到 FR8003A 屏蔽罩（这是本机最容易出错的一步，先拍照）
2. 找到 FR8003A 的 TX / RX 两个脚
3. 逻辑分析仪 CH0 → WB32 的 PC10（TX 方向）
4. 逻辑分析仪 CH1 → WB32 的 PC11（RX 方向）
5. GND 必须共地
6. 采样率 ≥ 1 MHz（115200 波特率，10 倍余量足够）
7. 触发条件设成 RX 线上出现下降沿（起始位）

### 4.3 帧格式（Westberry `md` 协议）

```
[opcode] [payload...] [checksum]
checksum = (Σ opcode + payload) & 0xFF
```

- 多字节字段小端
- 载荷长度按 opcode 隐式确定，可变长帧内含长度字节
- **同步 ACK = `61 0D 0A`**（3 字节，无校验和），停止-等待式，一次一帧

### 4.4 主控 → 模块（WB32 → FR8003A）

| opcode | 名称 | 载荷 | 帧长 |
|---|---|---|---|
| `0xA1` | SEND_KB | 8 字节 boot 键盘报告 | 10 |
| `0xA2` | SEND_NKRO | 14 字节 NKRO 位图 | 16 |
| `0xA3` | SEND_CONSUMER | u16 LE usage | 4 |
| `0xA4` | SEND_SYSTEM | 1 字节位图 | 3 |
| `0xA6` | **DEVCTRL** | 1 字节子命令 | 3 |
| `0xA8` | SEND_MOUSE | 5 `[btn,x,y,wheel,pan]` | 7 |
| `0xA9` | SEND_DEVINFO | `[len][name…]` | var |
| `0xAB` | MANUFACTURER | `[len][str…]` | var |
| `0xAC` | PRODUCT | `[len][str…]` | var |
| `0xAD` | VPID | `(pid<<16)\|vid` LE | 6 |
| `0xAF` | RAW | `[0x61][32][32B]` | 36 |

### 4.5 `0xA6` DEVCTRL 子命令全表

| 子命令 | 名称 | 本项目固件是否发 | 发出位置 |
|---|---|---|---|
| `0x11` | USB | ✅ | `FUN_0800264c`、`FUN_08002864`、`FUN_080039fc` |
| `0x30` | 2.4G | ✅ | `FUN_080039fc` |
| `0x31`/`0x32`/`0x33` | BT1/BT2/BT3 | ✅ | `FUN_080039fc` |
| `0x34`/`0x35` | BT4/BT5 | ✅ | `FUN_080039fc`（隐藏通道） |
| `0x51` | PAIR | ✅ | `FUN_080039fc` |
| `0x52` | CLEAN（解除配对） | ✅ | `FUN_080039fc` |
| `0x53` | **INQVOL（查询电量）** | ✅ | **`FUN_08003ac8`** |
| `0x55`/`0x56` | BT 休眠 使能/禁用 | ✅ | `FUN_080042fc` |
| `0x57`/`0x58` | 2.4G 休眠 使能/禁用 | ✅ | `FUN_080042fc` |
| `0x64` | 充电中 | ❌ **未使用** | — |
| `0x65` | 充电停止 | ❌ **未使用** | — |
| `0x66` | 充电完成 | ❌ **未使用** | — |
| `0x70` | 模块固件版本 | ✅ | `FUN_080042fc` |

> `0x64`/`0x65`/`0x66` 原厂完全没发，这是键盘没有任何充电状态对外表现的原因。

### 4.6 模块 → 主控（FR8003A → WB32）

| opcode | 名称 | 载荷 |
|---|---|---|
| `0x5A` | INDICATOR（主机 LED 状态） | 1 字节位图 |
| `0x5B` | DEVCTRL（连接状态） | 1 字节子命令 |
| `0x5C` | **BATVOL（电量百分比）** | **1 字节 `0x00`–`0x64`** |
| `0x5D` | MD_FW_VERSION | 1 字节 |
| `0x60` | HOST_STATE（`0x01` = resume） | 1 字节 |
| `0xAF` | RAW（回传） | `[0x60][32][32B]` |

`0x5B` 连接状态子命令：`0x31` PAIRING · `0x32` CONNECTED · `0x33` DISCONNECTED · `0x36` REJECT

### 4.7 抓包时该看到什么

正常有线使用时的典型序列：

```
WB32 → MODULE : A6 11 11        (DEVCTRL / USB   → 校验和 0xA6+0x11+0x11=0xC8)
MODULE → WB32 : 61 0D 0A        (ACK)
WB32 → MODULE : A1 <8B report> <ck>
MODULE → WB32 : 61 0D 0A        (ACK)
...每 3 秒一次轮询：
WB32 → MODULE : A6 53 59        (DEVCTRL / INQVOL)
MODULE → WB32 : 5C <pct> <ck>   (BATVOL)
```

如果完全看不到帧，优先怀疑：接线反了（TX/RX 交换）、没共地、模块未上电、
示波器触发没抓到（试试电平触发而非边沿）。

## 5. 交叉验证：三层如何互相印证

这是本项目方法论的核心 —— **任何结论都至少在两层得到确认**。

| 结论 | L1 证据 | 固件静态分析 | L4 UART |
|---|---|---|---|
| 5 个蓝牙通道 | `via.json` 只声明 3 个，但键码区有 `DEV BT4/BT5` | 字符串 `MAX102 BT4/BT5` + `DEVS_BT4/5` 枚举 | `A6 34`/`A6 35` 帧 |
| 隐藏 BOOT 层 | `LAYER_COUNT=5`，第 5 层含 `QK_BOOT` | `FUN_0800BCB4` + magic `0xDEADBEEF` | — |
| 电量不上报电脑 | 无 HID 电量接口 | `0x5C` 只喂给 10 颗 LED 柱 | 只在无线模式每 3 秒轮询 |
| 三模走 UART 不直连 | — | 无蓝牙栈代码，只有 UART3 + `md` 协议 | 抓到 `61 0D 0A` ACK |
| 用的是 QMK | VIA 协议 v12 | bootloader 代码与 QMK 上游逐字一致 | — |

### 5.1 UART 协议是怎么被确认的

不是靠猜。三条独立证据链吻合：

1. **固件侧**：`FUN_080034d4` 里 `0x1c200` = 115200；`FUN_08003518` 是收帧解析器；
   `FUN_08003ac8` 发 `A6 53`
2. **上游侧**：`WestberryTech/qmk_westberry`（`tri-mode` 分支）的
   `keyboards/westberry/wireless/module.c` 里 `md` 协议实现**逐字节吻合**
3. **同族项目**：`dot-agi/fr8003-re` 对 FR8003A 的独立逆向结论一致

→ 所以**不需要逻辑分析仪就能确认无线协议**，逻辑分析仪只是在出问题时用来验证的。

> 注意：本项目**不做移植**。这套协议只用来**读懂固件行为**（比如电量从哪来），
> 改固件时用不着自己写 transport。

### 6.6 已知分析限制

1. **Ghidra 对间接调用识别不佳** —— 大量 `(*(code *)(...))(args)` 是被误判的普通调用
2. **没有符号表** —— 520 个函数全是 `FUN_0800xxxx`
3. **浮点/长整型内联代码混入** —— `FUN_08000244` 是 64 位除法而非业务逻辑
4. **数据区未完全分离** —— Ghidra 线性扫描把部分数据当成了代码

## 7. 三层调试的安全边界

| 操作 | 风险 | 可逆性 |
|---|---|---|
| 读 VIA（cmd 0x01/0x02/0x04/0x11/0x12…） | 无 | — |
| 写键位（cmd 0x05/0x13） | 键盘布局变了 | ✅ 可再改回，或 `EEPROM_RESET` |
| `EEPROM_RESET`（cmd 0x0A） | 键位+宏全丢 | ❌ 但可用备份 JSON 恢复 |
| 进 DFU（L2） | 键盘暂时不可用 | ✅ `-R` 复位即可 |
| DFU 读固件 | 无 | — |
| DFU 写固件 | **可能变砖** | ✅ DFU 可救（只要芯片没坏） |
| SWD 连 core | 一般无害 | ✅ 断开即可 |
| SWD 改 PC / 写 RAM | 固件跑飞 | ✅ 复位即可 |
| 焊接 CON2 排针 | 焊盘脱落风险 | ❌ 不可逆 |
| 拆电池排线 | 排线座损坏风险 | ⚠️ 小心操作 |
| 电池短路 | **起火** | ❌ 极度危险 |

**铁律：动 L2 之前，先把 `max102_stock_256k.bin` 复制到三个不同介质。**

## 8. 常见故障速查

| 现象 | 最可能原因 | 处理 |
|---|---|---|
| `wb32-dfu-updater -l` 找不到设备 | 没进 DFU / 缺 WinUSB 驱动 | 重按组合键；装 `dpinst_amd64.exe` |
| 进了 DFU 但驱动装不上 | 顺序错了 | **先进 DFU**，再装驱动 |
| 读到 256KB 但 MD5 不对 | `-Z` 给少了 / 读中途断开 | 重读，确认 `-Z 262144` |
| 写入后键盘无反应 | 起始地址不是 `0x08000000` | 重进 DFU 再刷，`-s 0x08000000` |
| 键盘彻底不响应 DFU | 冷启动状态残留 | 拔电池排线 10 秒重插 |
| VIA 网页连不上 | 没切有线模式 | FN + T |
| VIA 只显示 4 层 | 正常，第 5 层是隐藏 BOOT 层 | 设计如此 |
| OpenOCD 报 flash 操作失败 | WB32 无 flash 驱动 | 改用 DFU 刷，SWD 只做 core 调试 |
| 逻辑分析仪抓不到 UART | TX/RX 接反 / 未共地 | 交换 CH0/CH1，检查 GND |

## 9. 硬件事项（拆机前必读）

### 9.1 拆机步骤要点

1. **先断开电池排线**（10000mAh 锂电池，短路会烧板）
2. 记录每颗螺丝位置（键盘通常有不同长度螺丝，装回时搞错会顶穿 PCB）
3. 拆键帽时先拍照，尤其是空格/回车这类带卫星轴的
4. 拔排线用塑料撬棒，不要用金属

### 9.2 需要拍照确认的点

| 位置 | 为什么 |
|---|---|
| U7 主控近景（侧光 45°，丝印清晰） | 确认 `WB32FQ95` 批次 |
| 整块 PCB 正面 | 看天线、测试点、第二颗芯片 |
| PCB 反面 | 电池、排线走向 |
| **无线模块屏蔽罩** | 确认 `FR8003A` 型号 |
| CON2 四针 | 焊盘间距（选排针规格） |
| X14076 充电 IC 周边 | 找 `CHRG` / `STDBY` 测试点 |

### 9.3 已确认的硬件清单

| 丝印 | 器件 | 说明 |
|---|---|---|
| U7 | `WB32FQ95` | Cortex-M3，256KB Flash，QFP48 |
| U8 (SOP8) | SPI Flash | 可能存灯效资源或配置 |
| FR8003A | 富芮坤 BLE5.1 + 2.4G SoC | 无线模块，屏蔽罩内 |
| X14076 | 充电管理 / 保护 IC | 电量与充电状态源头 |
| `LED71`…`LED104` | RGB LED | 丝印至少编到 104；**固件里总数是 115** |
| `DW34/DW43/DW44/DW57` | 二极管阵列 | 矩阵防鬼键 |
| CON2 | `GND SWCLK SWDIO 3.3V` | SWD 调试焊盘 |
| CON3 | `3.3V` | 额外电源测试点 |
| Y1 | 晶振 | — |
| PCB 丝印 | `MA102-QMK-V1 / 2025 05 26` | 厂家自己印了 `-QMK` |
