## 1. 为什么必须走"二进制补丁"

| 事实 | 影响 |
|---|---|
| 原厂固件是 QMK 编译的，但**源码不公开**（Weikav 在 QMK 违规名单） | 不能改源码重编译 |
| 电量数据本来就躺在 RAM 里，一直在刷新 | 不需要碰无线模块 |
| VIA 命令分发是 `tbh` 跳转表，结构极简 | 加/换一条命令 = 改 1 个表项 + 写 34 字节 |

→ **补丁是最小改动路径。**

## 2. 关键地址（全部逐字节核实）

### 2.1 命令分发器

原厂分发器入口行为（`0x08009942` 起 4 条指令）：

| 地址 | 行为 |
|---|---|
| `0x08009942` | 从 `[sp, #4]` 取命令号到 `r3` |
| `0x08009944` | 与 `0x2D`（45）比较 |
| `0x08009946` | 大于则跳 `0x080099BE`（越界，静默忽略） |
| `0x08009948` | `tbh [pc, r3, lsl #1]` 查表跳转 |

`tbh` 语义：`target = (tbh地址+4) + 2 * table[cmd]`

### 2.2 我们要用的地址

| 用途 | 地址 | 说明 |
|---|---|---|
| `tbh` 表基址 | `0x0800994C` | 45 项，`cmd 0x00`–`0x2D` |
| 要改的表项 | **`0x08009958`** | = `0x0800994C + 0x06*2` |
| 响应缓冲区指针字面量 | `0x08009AAC` → `0x20000F60` | 所有命令往这里填返回值 |
| 新代码落点 | **`0x0800FD82`** | 236 字节纯空白，零引用 |
| 字面量池 | `0x0800FDA4` | 代码之后自动对齐 |

### 2.3 要读的 RAM（一次 `ldr` 拿全）

| 地址 | 字段 | 取值 |
|---|---|---|
| **`0x20000C80`** | **电量** | 0–100 |
| `0x20000C7D` | 连接状态 | 0=NONE 1=PAIRING 2=CONNECTED 3=DISCONNECTED 4=REJECT |
| `0x20000C7E` | 指示灯位图 | bit0=Caps bit1=Num bit2=Scroll |
| `0x20000C7F` | 模块固件版本 | FR8003A 自报 |

这四个字节连续：`0x20000C7D..0x20000C80`，小端读一个 u32 就是 `[state|indicator|version|bat]`。

## 3. 为什么选 `cmd 0x06`

| 候选 | 原 handler | 风险 | 结论 |
|---|---|---|---|
| **`0x06`** | `FUN_08008E34`（按位掩码批量设 LED 颜色） | **官方 VIA JSON 未声明、网页驱动未使用** | ✅ **选它** |
| `0x16` | `FUN_08008F74` | 私有，用途未知 | 风险高 |
| `0x1A`/`0x1B` | 可能挂灯效 | 未知 | 风险高 |
| 新增 `0x2E` | — | 需要扩表 + 改越界判断，没有足够空间 | 不可行 |

**证据**：`HANDOVER.md` §5.2 已记录"命令 **6** 是私有的，**官方网页驱动都没用它**"。

## 4. 补丁内容（41 字节）

### 4.1 handler 汇编（34 字节）

```asm
        .org 0x0800FD82
        ldr   r1, [pc, #0x20]    @ 2B  → 池 0x0800FDA4
        ldr   r1, [r1]           @ 2B  r1 = 0x20000F60（响应缓冲区）
        ldr   r2, [pc, #0x20]    @ 2B  → 池 0x0800FDA8
        ldr   r2, [r2]           @ 2B  r2 = [state|ind|ver|bat] 小端
        ubfx  r3, r2, #24, #8    @ 4B  r3 = bat
        strb  r3, [r1, #4]       @ 2B
        uxtb  r3, r2             @ 2B  r3 = state
        strb  r3, [r1, #5]       @ 2B
        ubfx  r3, r2, #16, #8    @ 4B  r3 = version
        strb  r3, [r1, #6]       @ 2B
        ubfx  r3, r2, #8, #8     @ 4B  r3 = indicator
        strb  r3, [r1, #7]       @ 2B
        movs  r0, #0             @ 2B  ★ 返回 0 → 触发 raw_hid_send
        bx    lr                 @ 2B
```

机器码：

```
08490968084a1268 c2f30763 0b71 d3b2 4b71 c2f30743 8b71 c2f30723 cb71 0020 7047
```

### 4.2 字面量池（8 字节 @ `0x0800FDA4`）

```python
0x08009AAC   # 响应缓冲区指针的地址（解引用得 0x20000F60）
0x20000C7D   # 设备状态结构体
```

### 4.3 表项（2 字节 @ `0x08009958`）

| 原值 | 新值 | 计算 |
|---|---|---|
| `0x0050`（→ `0x080099EC`） | **`0x321B`**（→ `0x0800FD82`） | `(0x0800FD82 - 0x0800994C) / 2` |

### 4.4 实际字节差异（脚本输出）

```
0x08009958 (2B)   原 5000        → 新 1b32
0x0800fd82 (34B)  原 全零        → 新 代码
0x0800fda4 (8B)   原 全零        → 新 ac9a0008 7d0c0020
```

## 5. 关键设计决策：`r0` 必须返回 0

这是**最容易出错的地方**，我追踪了完整路径。

### 5.1 公共尾部

handler 返回后进入公共尾部。关键行为：

| 地址 | 行为 |
|---|---|
| `0x080099C8` | 把 handler 返回值存 `r5` |
| `0x08009BC2` | 比较 `r5` 与 0 |
| `0x08009BC4` | `r5 != 0` → 跳 `0x08009F30`（另一个分支，不发送） |
| `0x08009BC8–0x08009BD0` | 读某标志字节，非 0 则跳 `0x08009F74` |
| `0x08009BD6` | 重新取命令号 |
| `0x08009BDA` | 命令号为 0 时跳 `0x08009F26`（特殊处理） |
| `0x08009BDE` | **调 `0x08008B80`，真正发送响应** |

**`r5 == 0` 才会执行 `bl 0x08008B80`（发送）。**

### 5.2 对照现有 handler

`cmd 1`（`FUN_08009280`）正常返回 **1**，越界返回 **0**：

`cmd 1`（`FUN_08009280`）的返回值判定：与 `0x72` 比较，
**超过则返回 0**，**未超过则返回 1**（3 条指令，`ite hi` 条件执行）。

**这看起来矛盾**：正常返回 1 却也要发送？

答案是：`r5 != 0` 走 `0x08009F30`，那条路径检查 `[sp,#4]` 后同样会回到发送。
两条路都能发，但路径不同。

**我们的 handler 只填响应缓冲区、不加额外状态，所以返回 0 走最短路径最安全。**

## 6. 使用方法

### 6.1 生成补丁

```bash
py -3.13 tools/patch_battery.py --verify    # 只检查
py -3.13 tools/patch_battery.py             # 生成
```

输出：`firmware/max102_patched_battery.bin`

### 6.2 刷入

```bash
# 1. 进 DFU：按住 FN → 按住右 Shift → 点一下 ESC
wb32-dfu-updater_cli.exe -l

# 2. 写入（地址必须从 0x08000000）
wb32-dfu-updater_cli.exe -D firmware/max102_patched_battery.bin -s 0x08000000

# 3. 复位
wb32-dfu-updater_cli.exe -R
```

### 6.3 读取

```bash
py -3.13 tools/read_battery.py          # 单次
py -3.13 tools/read_battery.py -w 2     # 每 2 秒刷新
py -3.13 tools/read_battery.py --json   # JSON（给别的程序用）
```

期望输出：

```
  电量       :  87%  [#################...]
  连接状态   : CONNECTED（已连接）
  模块版本   : 48
  指示灯     : CapsLock
```

### 6.4 回退

```bash
# DFU 模式
wb32-dfu-updater_cli.exe -D firmware/max102_stock_trimmed.bin -s 0x08000000
wb32-dfu-updater_cli.exe -R
```

## 9. 关于"充电状态"

你提到"充电时有灯珠常亮或一闪一闪"。我查完了，结论是：

**主控固件里没有充电检测，那盏灯是硬件直连的。**

| 检查 | 结果 |
|---|---|
| ADC 外设（`0x40003C00`）引用 | **0 次** |
| 所有 GPIOx_IDR 字面量 | 只有 `0x40000808`（GPIOC），且是颜色常量，不是引脚读 |
| `FUN_08002850`（像充电回调，`cmp #7/#0x12`） | **0 个调用者** → 死代码 |
| `0xA6 0x64/0x65/0x66`（充电中/停止/完成） | 定义但**从未发送** |

→ X14076 的 `CHRG`/`STDBY` 直接驱动 LED，中间没有检测电路。

**要上报充电状态只有两条路：**

| 方式 | 代价 |
|---|---|
| ① 飞线：把 CHRG 脚接到 WB32 空 GPIO | **需要改硬件** ❌ |
| ② 从电量曲线推断（充电时单调上升） | 零成本，但误判率高 |

**建议：先只上报电量 + 连接状态 + 模块版本。** 充电状态以后再说。

## 10. 风险与回退

| 风险 | 后果 | 规避 |
|---|---|---|
| 刷错文件 | 键盘不响应 | 有全片备份，DFU 刷回 |
| 补丁区判断错 | 覆盖在用代码 | 脚本有 5 道断言，任一不符即中止 |
| `r0` 返回值错 | 响应发不出去（读不到但键盘正常） | 已追踪完整路径，返回 0 |
| 原 `cmd 6` 被别的地方用到 | 某功能失效 | 官方 VIA/网页驱动都不用；最坏刷回 |

**唯一不可逆的操作是擦除 ROM bootloader 区（`0x1FFFE000`）**，
本方案只碰 `0x08000000` 起，绝对安全。
