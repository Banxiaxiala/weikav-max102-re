# 改固件流程 —— 在原厂二进制上打补丁

> 这一份是**操作手册**：拿到一个新需求后，怎么从"想加个功能"走到"刷进键盘并验证"。
>
> 完整样例（电量上报）见 [08-电量补丁方案.md](08-电量补丁方案.md)。
> 环境准备见 [01-环境与工具链.md](01-环境与工具链.md)，
> 地址/函数/寄存器依据见 [05-反汇编.md](05-反汇编.md) 与 [06-硬件引脚.md](06-硬件引脚.md)。

---

## 0. 为什么只能打补丁

原厂固件是 QMK 编译的，但**厂商从未公开源码**，所以：

- ❌ 不能改源码重编译
- ❌ 不能做 QMK 移植
- ✅ **只能按字节改已经编译好的二进制**

好消息是这条路完全够用：电量上报就是这么做的，只改了 **43 字节**。

---

## 1. 五步流程（总览）

| 步 | 做什么 | 产出 | 风险 |
|---|---|---|---|
| 1 | 定位：找到要改的函数 / 表项 / 数据地址 | 地址 + 反编译片段 | 读操作，零风险 |
| 2 | 选址：找可写的空白区或可替换的短指令 | 空白区区间 + 引用检查 | 零风险（只读分析） |
| 3 | 编写：写 handler / 改表项 | 字节序列 | 零风险（离线） |
| 4 | 校验：反汇编确认、边界检查、MD5 比对 | 补丁固件 | 零风险（离线） |
| 5 | 刷写：DFU 写入 + 工具验证 | 实机结果 | **唯一有风险的一步** |

前四步全在离线完成，出错顶多是白忙；只有第 5 步会动到设备。

---

## 2. 第 1 步：定位

### 2.1 先想清楚"改哪一类"

| 需求类型 | 通常落点 | 例子 |
|---|---|---|
| **新增一条 VIA 命令** | `tbh` 跳转表 + 空白区 handler | 电量上报（`cmd 0x06`） |
| 改已有命令的行为 | 原 handler 里的某几条指令 | 改 keymap 读写的边界 |
| 加一个状态上报 | 找轮询点 / 中断，往响应缓冲区填值 | 充电状态 |
| 改键码语义 | `QK_KB` 跳转表 | 给 `0x7E09` 之类未知键码赋义 |

**加新命令是最安全的**：完全不碰原有逻辑，只是"多挂一个 case"。

### 2.2 找地址的手段

| 手段 | 适合找什么 |
|---|---|
| Ghidra 全文搜索字符串 | 设备名、USB 描述符、错误信息 |
| 搜索外设基址常量 | 某外设的所有使用者（如 `0x40008400` = UART3） |
| 看 `literal pool` | 全局变量地址（RAM 变量都从这里 `ldr`） |
| 从已知函数往下追 | 分发器 → handler → 子函数 |
| `tbh` 表反查 | 某个 cmd 对应哪个 handler |

### 2.3 定位时必须回答的问题

- 数据在哪个地址？（RAM 变量 / 外设寄存器）
- 数据什么时候被更新？（主循环 / 定时器 / 中断）
- 有没有别人在读同一块缓冲区？（避免覆盖）
- 目标 handler 的**调用约定**是什么？（`tbh` 直接跳入 ≠ `bl` 调用）

> ⚠️ 最后一条踩过坑：handler 由 `tbh` **直接跳入**，不在 `bl` 上下文里，
> 所以**绝不能 `bx lr` 返回**，必须 `b` 回公共尾部。详见
> [08-电量补丁方案.md](08-电量补丁方案.md) 开头那段教训。

## 3. 第 2 步：找可写空间

### 3.1 优先找"全零空白区"

有效固件只到 `0x08010D33`，之后全是 `0x00`。空白区集中在尾部。

选择条件：

- 目标地址之后**至少**要放得下 handler 长度
- 区间内容**全为 `0x00`**（真正的空）
- 区间**没有被任何指针引用**（数据段里不能有指针指向它）

### 3.2 引用检查怎么做

```bash
# 扫全片，找是否有人指向候选区间
py -3.13 - <<'EOF'
import struct
d = open('firmware/max102_stock_trimmed.bin','rb').read()
base, lo, hi = 0x08000000, 0x0800FD82, 0x0800FE6E   # 候选区间
hits = []
for off in range(0, len(d)-4, 4):
    v = struct.unpack_from('<I', d, off)[0] & ~1
    if lo <= v < hi:
        hits.append((base+off, v))
print('hits:', hits)
EOF
```

结果为空才说明这块区域是**死的**，可以安全占用。

### 3.3 另一个思路：挤掉一条无用指令

如果空白区放不下，可以找**永不到达的分支**或**无副作用的冗余指令**来腾空间。
这种改法风险高得多，本项目暂未使用。

## 4. 第 3 步：编写补丁

### 4.1 结构（以 VIA 新命令为例）

```
① 跳转表表项（2 字节，halfword）
   原值指向某个已有 handler，改成指向新 handler

② 新 handler（几十字节，放在空白区）
   读数据 → 填响应缓冲区 → movs r0,#0 → b 公共尾部

③ 对齐填充（可选，1–2 字节 0x00）

④ 常量池（可选，4n 字节）
   ldr [pc,#imm] 需要的地址常量
```

### 4.2 表项计算公式（`tbh`）

```
target = (tbh 地址 + 4) + 2 * 表项值
表项值 = (target - (tbh 地址 + 4)) / 2
```

`0x08009948` 处的 `tbh` → 基址 `0x0800994C`，表项值必须是 `0..0xFFFF`（halfword）。

**新表项要落在哪里**：表项数组在 `0x0800994C` 起，每项 2 字节，
`cmd N` 对应 `0x0800994C + 2*N`。想接管 `cmd 6` 就改 `0x08009958`。

### 4.3 寄存器坑（ARM Cortex-M3，Thumb-2）

| 坑 | 说明 |
|---|---|
| `bx lr` | `tbh` 跳入时 `lr` 是**外层调用者**，`bx lr` 会直接跳飞 |
| 栈对齐 | 公共尾部会 `add sp,#0x34`，handler 里不能动 `sp` |
| `r4–r11` | 公共尾部会 `pop`，handler 里改了不还原就串数据 |
| `ldr [pc,#imm]` | 偏移必须按 `pc+4` 对齐计算，立即数范围小 |
| `movs` vs `mov` | 要返回值用 `movs r0,#0`，别写成 `mov r0,#0`（部分编码不带 flag） |

### 4.4 编写完必须自己反汇编一遍

```bash
py -3.13 tools/patch_battery.py --verify
```

脚本会做：长度检查 → 原值检查 → 空白区检查 → 引用检查 →
范围检查 → 反算回跳校验 → Capstone 反汇编比对。

## 5. 第 4 步：校验清单

在刷之前，逐项确认：

- [ ] 补丁后文件**尺寸不变**（不会触发 DFU 写入长度问题）
- [ ] 差异字节**只落在预期地址**（`cmp` 差异区间）
- [ ] 原有字节区**未被覆盖**（尤其 `0x08000000–0x08010D33` 有效区）
- [ ] 新 handler 的反汇编**与手写源码一致**
- [ ] 常量池地址**指向正确**
- [ ] 表项值在 `0..0xFFFF` 内
- [ ] 原厂固件备份**已经在手边**（`max102_stock_256k.bin`）

> 关于"尺寸不变"：`max102_patched_battery.bin` 与原厂 trimmed 同为 69,632 字节，
> 校验 MD5 只变了预期字节。

## 6. 第 5 步：刷写与验证

```bash
# 1. 进 DFU：按住 FN → 按住右 Shift → 点一下 ESC
wb32-dfu-updater_cli.exe -l

# 2. 写入（地址必须从 0x08000000）
wb32-dfu-updater_cli.exe -D firmware/max102_patched_battery.bin -s 0x08000000

# 3. 复位
wb32-dfu-updater_cli.exe -R
```

验证：

```bash
py -3.13 tools/read_battery.py
```

回退（任何时候都能做）：

```bash
wb32-dfu-updater_cli.exe -D firmware/max102_stock_trimmed.bin -s 0x08000000
wb32-dfu-updater_cli.exe -R
```

## 7. 失败模式与对策

| 现象 | 可能原因 | 对策 |
|---|---|---|
| 刷完键盘没反应，也进不了 DFU | 补丁破坏了启动路径 | 断电池等 10 秒 → 按住 `FN+右Shift` 插线 → 点 ESC |
| 能打字但新命令无响应 | 表项算错 / handler 没走到公共尾部 | 刷回原厂，重算表项 |
| 键盘随机死机 | handler 改了 `r4–r11` 或动了 `sp` | 刷回原厂，检查寄存器保存 |
| 只有个别键异常 | 误覆盖了键位数据区 | 比对差异字节，确认没越界 |
| DFU 工具报长度错误 | 用全片 256KB 写了 trimmed 的地址 | 用 trimmed 刷，或 `-Z` 显式给长度 |

**底线**：ROM DFU bootloader 在 `0x1FFFE000`，不可擦写，
**只要没动那片区域，芯片永远救得回来**。
